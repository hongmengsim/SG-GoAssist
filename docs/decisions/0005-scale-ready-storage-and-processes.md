# 0005. Build for scale from the start: async storage ports, then shared services

Status: accepted by CE2 on 1 Oct 2026. All four steps are built. What is proven and what is not is in each step and in the definition of done below. The teammate has not reviewed it yet.

## Decision

Keep the architecture (contract-first messages, the Pi as safety authority, repository and event-bus seams, roles). Do not rewrite it. Change the parts that would stop it running as several backend processes, while the code is still small:

1. **Async storage ports** (built, 1 Oct 2026). Every storage interface returns promises: `CaseRepository`, `DocumentTable`, `OperationsData`, the audit read, retention and the legacy import. The case service and everything that calls it became asynchronous. SQLite is still the adapter, so behaviour is unchanged; a network database (Postgres) can now be added as another adapter without touching the services.
2. **Shared event bus** (built, 1 Oct 2026; also checked against a real Redis server in WSL with two real backend processes, `npm run check:multi-process`: an event posted to one process reaches an operator on the other exactly once, and a scoped operator still sees nothing outside its scope). `MessageBroker` port (`events/broker.ts`), `BrokerEventBus` (`events/brokerEventBus.ts`: same delivery rules as the in-process bus, de-duplicates per handler, never throws into a request), `RedisBroker` (`events/redisBroker.ts`, over any ioredis-shaped client; ioredis is loaded only when chosen and is not a dependency), and `GOASSIST_EVENT_BUS=memory|redis` (`events/eventHub.ts`; an unknown value is refused). A gateway test shows a WebSocket client receiving an event another process published. Limits of a broker: delivery is asynchronous, events on different topics may arrive out of order, and delivery is at most once. See `docs/runbooks/multi-process.md`.
3. **A shared, re-entrant lock** (built, 1 Oct 2026). `KeyedLock` port (`concurrency/keyedLock.ts`): `InProcessKeyedLock` (FIFO per key, re-entrant through `AsyncLocalStorage`) and `DistributedKeyedLock` (queues in the process, then takes a lease with an expiry from a `LeaseStore`, renews it while the work runs, releases it after). `SqliteLeaseStore` keeps leases in a `locks` table with one atomic statement per operation; a Postgres or Redis store implements the same three operations. It replaces the per-service mutexes (`KeyedMutex` is deleted) and also restores the atomicity the case service lost when it went asynchronous: every read-modify-write in it (signals, requests, telemetry, actuator status, operator actions, feedback, the stale-case refresh and command expiry) runs under one `case-service` lock; autonomous vehicle changes lock per bus and docking observations per bus. Keys: `report:<kind>:<bus>`, `halt:<bus>`, `bus:<bus>`, `stop:<stop>`, `case-service`, `vehicle:<bus>`, `docking:<bus>`. Bus work takes the bus key before a stop key, always. `GOASSIST_LOCKS=memory|database` (`GOASSIST_LOCK_TTL_MS`, `GOASSIST_LOCK_TIMEOUT_MS`); an unknown value, or `database` without SQLite, is refused. Tests: 23 for the locks (including two connections on one file losing no updates, with the same code failing without the lock, crash expiry, renewal, timeout), and a burst of 20 simultaneous passenger requests ending on one case with nobody lost, where the same burst without the lock races. Limits: a lease guards against a crashed holder, not against work that outlives its renewals (keep locked work short); the case service takes one global lock, so its throughput is serial (the volume there is low; the high-rate bus path is separate); leases in a SQLite file only exclude processes on the same machine until the lease store moves to a network database.
4. **No domain state in process memory** (built, 1 Oct 2026). The legacy passenger-request state that lived in module-level maps is now in `OperationsData`: `requests` (indexed by bus and status), `vehicleStatuses`, `announcements` and the assistant `diagnostics` (30-day expiry kept; deletion tokens kept); all four are trimmed by the retention policy. `aviator.ts` became asynchronous; requests come back as copies, so a caller that changes one saves it, and the case link is attached under the request's lock so it cannot overwrite a status another process just set (`attachCaseToRequest`). `waitForRequestStatus` listens on the shared event bus and also re-reads the request every 250 ms, so an acknowledgement handled by another process, or a lost push, still wakes it. The bus-movement bridge is awaited. `/health` counts requests and active cases from counters instead of reading them. What is left in memory is deliberate and per process: WebSocket connections and their subscriptions, the bridge from case and request events to the event bus, rate-limit and metrics counters (so a limit applies per process), and the simulated bus's auto-acknowledge timer (it fires in the process that created the request). Tests: 6 in `requestState.test.ts` (restart, bus index, a waiter woken by a change made elsewhere with no push, by a bus event, and by timeout; the attach race).

5. **A Postgres adapter** (built, 1 Oct 2026). `PostgresDocumentTable` (JSON text plus numbered index columns, insertion order through a sequence column), `PostgresCaseRepository` (same columns and indexes as SQLite), `PostgresLeaseStore` (one atomic statement per lease operation, expiry on the database clock so machines with different clocks agree), `PostgresAuditLog` (buffered multi-row writes; a read writes the buffer first), and generic `Document*Repository` classes for bus status, bays and per-bus records, so the bus-operations data needs no hand-written SQL. Tables are created on first use inside an advisory-locked transaction so several processes starting at once do not collide. `GOASSIST_DATABASE_URL` selects it (unless `GOASSIST_STORAGE_DRIVER=sqlite|memory`); `pg` is loaded only then and is not a dependency. The contract tests run one suite against every adapter, and the Postgres ones run when `GOASSIST_TEST_DATABASE_URL` is set. Text, not jsonb, is used for the record body because the services compare records as strings and jsonb would reorder keys.

6. **Lock-free hot path** (built, 1 Oct 2026). Most bus reports are repeats that only carry a newer time. A new atomic step, `compareAndPut` on the keyed tables (and `compareAndUpsert` on the bus repositories, implemented for memory, SQLite and Postgres), writes only if the stored record is still exactly what the caller read; an older report is answered from the read alone. A bus status or ramp/decision/help report that is stale or a repeat therefore needs one read and at most one swap and takes no lock lease; a real change still takes the lock. If anything changed the record between the read and the swap, the swap fails and the report takes the locked path, so correctness is unchanged. Trade: a repeat no longer re-applies the bay, which only changes when the bus's facts do. Tests: the swap on every adapter, including ten simultaneous swaps from one read where exactly one wins (on Postgres too).

## Definition of done

A Postgres adapter and a Redis event-bus adapter exist, and the end-to-end scenario and the load test pass with **two backend processes** sharing them. Status, 1 Oct 2026 (Windows laptop, Postgres 14 and Redis in WSL on the same machine):

- **Passed:** `npm run check:multi-process` starts two real processes on shared Postgres, Redis and database locks: events cross processes exactly once, a bus status posted to one is readable from the other, audit events are visible from both, and 20 passengers asking at once through both processes end on one case with nobody lost; the control run with per-process locks shows the race (for example 2 cases, 11 of 20 intents).
- **Passed, one process:** the whole end-to-end scenario (both simulated buses, halts, timeouts, audit) on Postgres with database locks.
- **Passed, two processes (`npm run e2e:scenario:two`):** the same whole scenario with the passenger and Bus 1 on process A and the operator and Bus 2 on process B, sharing Postgres, Redis and locks. A request made on A is delivered to Bus 2's agent on B, operator halts and bay grants made on B reach Bus 1 on A, and the audit trail read from B holds all 196 events in order.
- **Load test** (`npm run load:test -- --processes N`, bus status ingest, p95 under 100 ms): with the lock-free hot path one process sustains 600 msg/s (p95 15 ms) and saturates near 900; two processes sustain 1,000 msg/s (p95 18 ms) and saturate near 1,300. Before the hot-path change the figures were 300 and 600. The gain from a second process is smaller than 2x here because the load generator, both backends, Postgres and Redis all share one laptop.
- **Not done:** any test with the processes on separate machines, more than two processes, and any claim about 3,000 msg/s.

Until the scenario and the load test have both run against two processes, no multi-process claim beyond the list above is made.

## What step 1 changed

- `backend/src/storage/documentTable.ts`, `backend/src/cases/*`: ports and adapters are async.
- `backend/src/services/operationsData.ts`: `getOperationsData()`, `configureOperationsData()` and `resetOperationsData()` are async; `ready` resolves once old data is imported and retention has run; `getAuditLog()` gives synchronous access for fire-and-forget audit writes; the server starts listening only after the data is ready.
- The audit log write stays synchronous (write-behind, batched); its read is async.
- About 40 call sites in seven services, four routes and the WebSocket gateway were converted. The conversion was made with a type-aware tool that adds `await` to every unawaited promise, so no call was missed silently; the array-callback and constructor sites it cannot handle were fixed by hand.
- Tests: the backend tests pass (341), including the teammate's case-service tests, converted mechanically (`assert.throws` on a call became `await assert.rejects`).

## Cost and risk

The change touches most of the teammate's case service. There is no behaviour change intended. Async handlers can interleave where synchronous ones could not (two messages for the same case could run their read-modify-write concurrently in one process). Step 3 fixed that with the shared lock; between step 1 and step 3 the risk was real (the control test in `assistanceConcurrency.test.ts` shows it).
