# Reviews of 1 Oct 2026: security, backend code, Pi agent, operator console

Four independent read-only reviews (security, backend code, Pi agent, operator console) of the work since commit `13acadc` (the storage, async, lock, event-bus and Postgres changes, the Pi bus agent, and the operator console). Each reviewer read the code; **none of the findings below has been reproduced by running it** unless the status says so, and the fixes came afterwards (1 Oct 2026, each with a test written first). The Status column says what was done; "open" means untouched and "deferred" means a decision or hardware is needed first.

How to read the columns: "Cause" says whether the finding comes from this stretch of work ("new"), was already in the code ("existing", mostly the passenger and simulator routes the project started with), or is a design gap. Severity is the reviewer's, with the reviewer's own uncertainty kept in the text.

Nothing in the Pi or console reviews or the security review was rated CRITICAL. The Pi safety gate itself was found fail-safe (details at the end).

## Pi bus agent review

| P-H1 | HIGH     | new      | A stale cached operator-halt poll can release a halt that a WebSocket push just set: `_pull_halt` overwrites the flag with a cache that is 0 to 10 s old. ## Backend code review

The reviewer's verdict was to block on K-H1 to K-H3 before relying on the Postgres or multi-process deployment (K-H1 also affects the default SQLite one). No CRITICAL findings.

| ID   | Severity | Cause | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Status                                                                                                                                                                                        |
| ---- | -------- | ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| K-H1 | HIGH     | new   | The same crash as S-H1: bare `async` Express 4 handlers (`routes/assistance.ts`, `assistantDiagnostics.ts`, `location.ts`, `passenger.ts`, `/health`) turn any rejection into a process exit, and there is no `unhandledRejection` handler. Possible unauthenticated trigger: `POST /simulator/command` with `{}` reaches `get(undefined)`, which node:sqlite probably refuses to bind (not run). | K-H2 | HIGH     | new   | The same as S-M8: a `pg` pool with no `error` listener kills the process when an idle connection dies (database restart or failover).                                                                                                                                                                                                                                                                                                                                          | fixed (see S-M8)                                                                                                                                                                              |
| K-H3 | HIGH     | new   | Per-bus request lookups read the OLDEST 500 rows (`find` is ascending with a limit), so once a bus has more than 500 stored requests the bus's fallback poll never sees new ones, duplicate suppression looks only at old ones, and the audio announcement misses the newest acknowledged request (`aviator.ts:183-214, 466`, `routes/busOperations.ts:104`). | K-M2 | MEDIUM   | new   | The lock-free heartbeat swap can race the locked write path on Postgres or with several processes: the locked path reads, awaits `applyBay`, then writes with a plain `upsert`, so a heartbeat can commit in the gap and an older report then overwrites it (self-heals on the next report). | K-M3 | MEDIUM   | new   | The WebSocket subscribes after awaiting the snapshot (`SUBSCRIBE`, `SUBSCRIBE_CASE`), so a change in the gap is lost, and a socket that closes during the await gets its subscriptions re-added for good. | K-M4 | MEDIUM   | new   | Retention trims commands, statuses, requests and observations by global insertion order, which can delete rows an open case still needs (a long-open case can lose its `DEPLOY_RAMP`, so a second deploy is issued), and archives cases with empty command lists. ## Suggested order

1. Anything that can crash or blind the safety path: P-H1, P-H2, P-H3, P-M1, P-M2, P-M5, P-M6 (Pi agent), and S-H1 = K-H1, S-M8 = K-H2 (backend process crashes, both introduced by the async and Postgres work), then K-H3 (new requests invisible to a bus after 500).
2. Anything that lets an operator do the opposite of what they meant, or leaks the operator token: C-H1, C-H3, C-H2.
3. Access control: S-H3 (start-up guard), S-H2, S-H4, S-M1 to S-M4.
4. The rest, in the order the reviewers listed them.

Fixes need a failing test first (repo rule), one concern per commit.
